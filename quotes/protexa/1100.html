Lo que entendemos.

El backend actual requiere documentar sus APIs para facilitar la construcción del frontend, sustituir Auth0 M2M y consolidar el acceso a datos. El problema de tokens y las dependencias de la réplica deben revisarse antes de modificar la solución.

Cómo lo solucionamos.

Documentar hasta cinco endpoints, utilizar Microsoft Entra ID existente para una API y un consumidor M2M, y conectar el backend a la DB original por la VPN existente, con un usuario dedicado de permisos mínimos.

Valor incluido.

OpenAPI/Swagger, colección Postman, guía de integración, manual técnico, bitácora de cambios y repositorio Git en DevOps. Trabajo asistido por IA con revisión humana, validación funcional, correcciones y evidencias de calidad.

La propuesta se basa en el archivo PTX-ModernizacionFacturacion.xlsx, hojas «Resumen de propuesta», «Actividades» y «Ahorros». No se altera la lógica funcional existente ni se incluye construir el frontend.

02 /Alcance y resultado esperado.

01. APIs documentadas

Un proyecto existente y hasta cinco endpoints. Contrato OpenAPI/Swagger, parámetros, esquemas, errores y seguridad; ejemplos y guía contrastados con código y respuestas reales.

02. Identidad corporativa

Una API y un consumidor M2M en un tenant corporativo: registros de aplicación, roles, validación de tokens, caché y adquisición automática de nuevos tokens. Las credenciales permanecen en servidor.

03. DB única

Acceso a la base original mediante VPN existente; usuario dedicado con permisos mínimos, conexión actualizada y retiro de réplica y sincronización solamente después de validar y obtener autorización.

Secuencia de implementación

Revisión del backend → contrato de APIs → identidad M2M → conexión a la DB original → pruebas integradas, despliegue y transferencia.

Se conserva un mecanismo de reversión hasta validar el cambio. La cancelación de Auth0 depende de que este proyecto y sus consumidores ya no requieran el servicio, y de confirmar contratos y otros usos.

07 /Supuestos y exclusiones.

  • Acceso a código y ambientes existentes desde el arranque; VPN operativa y administrador de Entra ID y DBA disponibles para permisos y consentimiento.
  • Un proyecto, hasta cinco endpoints, una API, un consumidor M2M, un tenant corporativo y una DB original accesible por VPN existente.
  • Se conserva la lógica funcional. No incluye frontend, nuevos endpoints, rediseño de datos ni migración de motor de base de datos.
  • M2M se ejecuta entre servicios y las credenciales quedan en servidor. La autenticación interactiva de usuarios del frontend se define y estima por separado si se requiere.
  • Retiro de réplica, sincronización y Auth0 coordinado con sus propietarios, después de validar dependencias y conservar una reversión. No se cancelan servicios automáticamente.
  • La reserva cubre ajustes menores con registro; cambios de alcance y otras mejoras requieren una nueva estimación. No se asume operación o soporte recurrente dentro de esta inversión.
